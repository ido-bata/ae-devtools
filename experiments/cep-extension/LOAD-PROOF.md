# LOAD-PROOF — CEP panel load & lifecycle proof plan (Issue #36, CAP058–CAP060)

> Status: **procedure definition, not yet executed.** This document fixes
> *what must be true* before a scaffolded CEP extension may be loaded into
> After Effects, and *what evidence counts* as load/lifecycle proof.
> Nothing here has run against a real AE session. Every claim stays
> `UNVERIFIED` until an authorized session produces the recorded evidence.

Scope: a scaffold generated by `scaffold.mjs` (CAP057). Native SDK plugin
load proof is a separate procedure (`experiments/native-sdk/LOAD-PROOF.md`).

## 1. Authorization gate (hard prerequisite)

A load proof may run **only** in an explicitly owned and authorized AE
session. Before any step below:

- [ ] The operator has named the session in writing (issue comment or
  equivalent): which AE installation, which OS user/account, and that it
  is dedicated to this proof — **never** the operator's interactive
  session.
- [ ] The proof uses a disposable extension folder and disposable AE
  state; the user's real panels/settings are never modified.
- [ ] `PlayerDebugMode` changes are recorded before/after and reverted;
  they are a development flag, not a permanent system change. Any consent
  or security dialog is decided by the owner — never automated.
- [ ] Windows is untouched — no Windows host exists for this work
  (Issue #21); Windows rows stay `UNVERIFIED`.

If any box is unchecked, the proof does not run.

## 3. Fixtures

- **F-C1 load fixture:** the scaffolded panel as-is. Success signal: the
  panel appears under Window > Extensions (or the host's extension list),
  `getCurrentApiVersion()` returns a `{major,minor,micro}` object, and
  `app.version` (attribute read, not a call) returns the AE version
  string via `evalScript`.
- **F-C2 error fixture:** the panel's "intentional error probe" button
  runs ExtendScript that throws; success signal is an `EvalScript_ErrMessage`
  (or equivalent typed error) surfaced to the panel, not a silent failure.
- **F-C3 lifecycle fixture:** panel reload (close/reopen or host reload),
  extension folder removal, and AE restart with/without the extension —
  each transition recorded.

## 4. Verification conditions

Each run records: AE version+build, OS, CSXS/CEP version actually loaded,
manifest hash, panel asset hashes, `PlayerDebugMode` before/after,
per-step outcome (`PASS`/`FAIL`/`BLOCKED`/`UNKNOWN`), timestamps, and
console/log captures where obtainable. Evidence lands in
`evidence/run-<date>/` in the same shape as `read-only-probe`.

Explicit checks:

1. **CSInterface provisioning** — resolved at scaffold level:
   `CSInterface.js` is bundled (official CEP_12.x file). The load proof
   still records whether the bundled copy loads and `new CSInterface()`
   succeeds; a host-provided resolution is not assumed or required.
2. **evalScript round trip** — `app.version` result equals the AE build
   string; the error probe produces the `EvalScript error.` sentinel
   surfaced as a typed error, not a hang.
3. **Reload semantics** — does closing/reopening the panel re-run
   `main.js`? Does AE cache the manifest (stale manifest after edit)?
4. **Unload/cleanup** — removing the extension folder + `PlayerDebugMode`
   revert leaves no residue; AE restart without the folder shows no
   phantom panel entry.
5. **No side effects** — the proof opens no project, mutates no user
   preference beyond the recorded `PlayerDebugMode` toggle, and quits
   nothing.

## 5. UXP rows (CAP060)

UXP plugin load/reload is **out of scope** until Adobe ships a released
AE build with documented plugin loading and remote IPC. Until then every
UXP lifecycle row is recorded `BLOCKED (no released-build surface)` —
never `PASS` by assumption, never scaffolded as if supported.
